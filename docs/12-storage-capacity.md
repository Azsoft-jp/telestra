# 12 / ストレージ容量・回線・費用の見積り

クラウドへ原本を保存すればHDD容量を小さくできるが、必要なアップロード帯域と障害時バッファはゼロにできない。保存額はStorageの容量と書込・読取・転送料、二次Replica、エンコード時の入出力を分けて見積もる。

## 入力パラメータ

- `R`: 録画ストリームの実測Mbps（地デジの設計初期値として15〜20Mbpsを仮定）。
- `N`: 同時録画数。
- `T`: 想定する回線停止時間（秒）。
- `H`: 1日あたり録画時間（時間）。
- `D`: 原本Retention日数。
- `F`: Encode後の容量比（プロファイルと内容に依存、必ず実測）。
- `C_rep`: 原本Replicaを何部置くか。

## 計算

- 生TS流量 = `R × N / 8` MB/s（Mbps/8、十進概算）。
- 必要なスプール下限 = `R × N × T / 8` MB + メタデータ/再送/安全余裕。
- 月間原本流入 = `R × 3600 × H × 30 / 8 / 1000` GB（十進概算）。
- 30日保持の定常状態なら保持原本≒直近30日分の流入量。初月の平均GB-monthはこれより少ないことがある。
- ダウンロード時間の概算は`sizeBits / effectiveDownlinkBps`。エンコード済みや字幕sidecarの総量を加える。

### 例（費用保証ではない）

`R=20 Mbps`、1日3時間×30日なら原本約810GB。`N=2`本で30分の回線停止を耐えるには、TSだけで約9GBのローカルスプールが必要。20GB程度の上限は一つの運用案だが、同時録画や回線復旧遅延で超過し得る。

保存先候補はR2、Backblaze B2、通常S3、ローカルNAS。配信頻度・読取料金・API呼び出し・リクエスト単価・外向き転送・最低保管期間・地域/レイテンシを最新料金表で比較する。

## 既定ポリシー案

- Raw original: 最初は自動削除なし。ユーザーのRetention設定後、検証済みで削除可能にする。
- Derived rendition: 再生成可能なのでLRU/容量上限を設定。ただし字幕と音声の正本は原本と別途保全。
- Replica: 原本に対して必要数の成功ACKを永続化。最小費用運用ではレプリカなしも選べるが「保全保証なし」と明示。
- スプール満杯: 静かに上書きせず録画を中止/失敗と表示し、再実行・手動復元の導線を提供。
- PWA: 容量推定と事前警告を行うが、ブラウザの利用可能容量値を保証としない。

## 見積り時の運用チェック

1. 受信TS実測ビットレート/同時録画数を記録。
2. Storage APIへの持続upload帯域・遅延・障害時のretryを計測。
3. 録画視聴回数、シーク頻度、PWA DL容量と配信回数を計測。
4. エンコード時のraw download+rendition uploadも帯域と課金へ計上。
5. API/DB/DO/Queue/Front secondaryの維持費を加算。
6. 料金と容量しきい値をアラート化、月額上限に近づいた際の保存ルールを利用者へ通知。
